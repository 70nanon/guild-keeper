# Guild Keeper 実装計画

## 現状と進め方

ゲーム仕様の参照元は [GAME_DESIGN.md](GAME_DESIGN.md) です。現在は **Phase 0 実装済み、Phase 1 と F-007 を v0.1 の実装 PR で検証済み** です。正式な機能完了は main マージ時となります。Phase 2 は F-008 の手動帰還を追加して検証中ですが全体は未完了で、F-009・F-010 と Phase 3 以降は未実装です。

各フェーズは長期的なロードマップ上の分類であり、厳密な着手順でもゲーム内のステージでもありません。同じ倉庫を継続して管理する設計を維持します。実際に選択・開発する単位、依存関係、進捗は [FEATURES.md](FEATURES.md) で管理します。

ユーザーが次に追加したいゲーム機能を選び、Codex が技術的な依存関係と内部タスクを整理します。依存機能が `main` で実装済みなら、後のフェーズの機能も、前のフェーズ全体の完了を待たずに選択できます。例えば倉庫表示があれば、Phase 2 の日次サイクル全体を待たずに Phase 3 の手動分類倉庫を検討できます。

各節の「前提フェーズ」は関連する基盤の参考であり、フェーズ全体の完了を要求するゲートではありません。実際の必須条件は `FEATURES.md` の各機能 ID で判定し、未決定事項は選択後・実装前に確認します。完了条件はそのフェーズの構想が揃った際の検証指針です。機能は原則 1 PR で実装・検証できる単位とし、ユーザーが明示的に選択するまで実装しません。未マージの実装は依存解消として扱いません。

実装前に関連仕様と既存コードを読み、対象範囲・未決定事項・受け入れ条件を確認します。以下の技術的考慮点は検討指針であり、未導入のライブラリ・保存方式・データ構造を確定するものではありません。未決定事項が動作に影響する場合は、必要な判断をユーザーに確認し、合意内容を記録してから実装します。

## Phase 0：開発基盤 — 実装済み

- **目的**：ブラウザゲームを開発・検証・公開する基盤を用意する。
- **前提フェーズ**：なし。
- **実装範囲・確認した現状**：React + TypeScript + Vite、Node.js 24.x、npm とロックファイル、Oxlint、タイトル「Guild Keeper」の準備中画面、PC・スマホを考慮した CSS が存在する。`vite.config.ts` のベースパスは `/guild-keeper/`。GitHub Actions は PR で Lint・ビルド、`main` への push で Pages デプロイを実行する。README・AGENTS あり。これは Phase 0 時点の基盤の記録であり、現在のゲーム機能・テストの状態は以下と FEATURES.md を参照。
- **技術的考慮点**：`npm ci` による再現可能な導入、サブパス配信、Pages に適した静的アプリ構成を維持する。Pages の Source は GitHub Actions を使用する。
- **完了条件**：依存導入、Lint、型チェックを含むビルド、開発・本番プレビューが動作し、Pages 配信と自動デプロイを確認できる。既存基盤ではこれらを確認済み。既存画面はゲーム UI の完成を意味しない。
- **テスト方針**：`npm run lint`、`npm run build`、本番 HTML と JS/CSS のサブパス配信、Actions の結果を確認する。v0.1 で Node.js 標準テストと Playwright を追加。
- **判断事項**：v0.1 は Node.js 標準テストと Playwright を採用。長期の対象端末・性能目標は今後決める。既存のビルド・配信方式を理由なく変更しない。

## Phase 1：最小限のピッキング — v0.1 基本操作を検証済み（体験評価未了・正式完了は main マージ時）

- **目的**：大量の在庫から注文品を探し、渡し、配置を工夫する最小の遊びを検証する。
- **前提フェーズ**：Phase 0。
- **実装範囲**：大きなインベントリ表示、初期アイテム生成、勇者ひとりからの注文、アイテム選択、注文品の納品、手動によるアイテム入れ替え。日送り・帰還・成長・自動化は含めない。
- **技術的考慮点**：アイテムの識別、配置、注文、選択状態を区別する。生成・注文適合判定・納品・入れ替えのゲームロジックを React の表示から分離し、テスト可能にする。タップで選択・入れ替え・納品できる操作を検討する。大量表示の性能を測り、必要な対策を判断する。
- **完了条件**：初期在庫と注文が表示され、合意したルールで選択・納品できる。手動入れ替えで品が消失・複製しない。PC とスマホでドラッグに頼らず一連の操作を行える。制限時間・ゲームオーバーを追加しない。
- **テスト方針**：生成データの整合性、注文適合・不適合、同一品の二重納品防止、入れ替え前後の在庫保存を検証する。選択から納品までの操作、PC・スマホ幅の表示と操作、大量件数時の応答を確認する。v0.1 では Node.js 標準テストと Playwright を導入済み。
- **プレイテスト（技術的完了条件と別に、実際のプレイで検証）**：大量のアイテムから目的のものを探す体験が楽しいか。操作や視認性にストレスがないか。探索が単なる苦痛になっていないか。観察した問題と調整案を記録し、自動テストの成功で代替しない。
- **判断事項**：初期件数・品目、個体と種類の区別、スタック、注文条件・数量、在庫不足・誤納品・部分納品、納品時の在庫処理、具体的なタップ操作、対象端末と性能目標。

## Phase 2：日次サイクル — F-007 と F-008 の手動帰還を検証済み（全体未完了）

- **目的**：同じ倉庫で仕事・入荷・整理を繰り返し、継続して遊べるようにする。
- **前提フェーズ**：Phase 1。
- **実装範囲**：注文完了の扱い、帰還によるランダム入荷、自由整理、任意の日送り、セーブ・ロード。
- **技術的考慮点**：注文・帰還・翌日の状態遷移を明確にし、操作の重複による二重入荷を防ぐ。抽選を再現可能にテストする手段を設ける。保存先・形式・バージョン・保存失敗時の対応を判断する。配置と在庫を日送りで初期化しない。
- **完了条件**：複数日を連続して進め、合意した順序で注文と帰還が処理される。整理を義務にせず、プレイヤーの操作で日を進められる。保存・復元後も日・在庫・配置・注文が整合する。
- **テスト方針**：日次遷移、二重操作、ランダム入荷の範囲、日をまたぐ在庫の保持、保存と復元の往復を検証する。未保存・不正データ・互換性・保存失敗の合意した対応も確認する。
- **プレイテスト（技術的完了条件と別に、実際のプレイで検証）**：プレイヤーが自発的に倉庫を整理したくなるか。整理によって次のピッキングが楽になるか。勇者によるランダム入荷が理不尽になっていないか。複数日遊んでも続けたくなるか。観察した問題と調整案を記録し、自動テストの成功で代替しない。
- **判断事項**：帰還と日送りのタイミング、未完了注文、返却と戦利品の抽選、容量超過、保存先・自動保存の有無・復旧・互換性、端末間同期の要否。

## Phase 3：整理の効率化 — 未実装

- **目的**：工夫とアップグレードによって作業方法が変わる体験を作る。
- **前提フェーズ**：Phase 2。
- **実装範囲**：アップグレードの購入・解放、ハイライト、分類倉庫、複数選択・一括移動。検索・フィルターは候補であり、このフェーズでの採用は未決定。
- **技術的考慮点**：解放状態の保存と旧セーブの扱い、倉庫間移動での在庫整合性、一括操作の途中失敗や容量不足の扱いを検討する。スマホの複数選択とスクロールを両立する。プレイヤー独自の分類を妨げない。
- **完了条件**：合意した解放条件・コストで機能を利用できる。解放状態を復元でき、ハイライト・複数選択・一括移動が正しく動作する。倉庫間で品が失われず、未解放機能が適切に扱われる。
- **テスト方針**：購入条件と重複購入、解放状態の復元、ハイライト対象の正確さ、一括移動前後の総在庫、容量不足・選択解除を検証する。PC・スマホで手作業との効率差と操作性を確認する。
- **判断事項**：報酬・通貨・経済、解放順・コスト、ハイライト条件、倉庫の容量と分類の自由度、一括移動の失敗単位、検索等の採用範囲。

## Phase 4：パーティ対応 — 未実装

- **目的**：依頼主と条件の増加によって、整理・探索の新しい課題を生む。
- **前提フェーズ**：Phase 3。
- **実装範囲**：複数冒険者、注文数の増加、アイテムの性能・属性、より複雑な条件のピッキング。戦闘やキャラクター育成は対象外。
- **技術的考慮点**：依頼主と注文の識別、条件判定の拡張、複数注文間の在庫競合、既存アイテム・セーブとの互換性を扱う。注文表示でインベントリが圧迫されないようにする。
- **完了条件**：複数冒険者の注文を区別して処理でき、性能・属性条件を満たす品だけを納品できる。同じ在庫が二重に割り当てられず、既存の日次・整理操作が動く。
- **テスト方針**：条件の組み合わせ・境界値、不適合品、依頼主の取り違え、競合する注文、セーブ移行を検証する。注文増加時のモバイル表示・応答性を確認する。
- **判断事項**：冒険者数、注文量、性能・属性の種類と比較規則、代替品の許容、予約や優先順位の有無。

## Phase 5：自動化 — 未実装

- **目的**：プレイヤーが自分の作業手順をルールにし、規模拡大に対応できるようにする。
- **前提フェーズ**：Phase 4。
- **実装範囲**：自動分類ルール、自動ピッキング、自動化の設定 UI。
- **技術的考慮点**：条件評価・実行処理を UI から分離する。競合や循環、再実行、手動操作との整合性を検討する。スマホでもルールを編集でき、実行結果を理解できるようにする。自動ピッキングと自動納品は同一とみなさない。
- **完了条件**：設定した条件に従って分類・ピッキングが実行され、保存・復元できる。競合・欠品時に合意した結果となり、品の消失・複製や無限処理を起こさない。手動操作を継続できる。
- **テスト方針**：条件一致・不一致、競合・循環・欠品・容量不足、再実行、手動操作との組み合わせ、ルール保存を検証する。大量在庫・多数ルールの応答と設定 UI の操作性を確認する。
- **判断事項**：ルールの表現、優先順位、実行契機、停止・修正・結果表示、予約在庫、自動納品の要否、解放条件・費用。

## Phase 6：生産・ギルド物流 — 未実装・長期構想

- **目的**：自動化で単純作業を減らし、多数の冒険者への装備配分と全体最適化を楽しめるようにする。
- **前提フェーズ**：Phase 5。
- **実装範囲**：強化・合成、大規模な装備管理、レイド準備、共通装備の配分。強化・合成の自動化、装備セット保存・一括配布、在庫管理・需要予測は採用を検討する候補。
- **技術的考慮点**：素材消費と生成、装備予約・配分・返却の整合性、ルールとの依存関係、大量データと保存形式の拡張を検討する。戦闘・経営シミュレーションを実装の前提にしない。
- **完了条件**：先に採用範囲とルールを合意する。その範囲で生産・確保・配分を一連に処理でき、素材や共通装備が二重に使われず、手動と自動の両方で既存の倉庫管理を継続できる。
- **テスト方針**：素材収支、生成結果、在庫不足、同時要求の競合、予約解除・返却、自動化との連携、セーブ互換性を検証する。大規模運用での性能とモバイル操作を確認する。
- **判断事項**：生産レシピ・強化規則、失敗の有無、レイド準備の条件、共通装備の利用期間・優先順位、セット機能・需要予測の採用、自動化範囲、対象規模。

## 成長・情報表現との整合性

2026-10-22 の企画統合では、仕事で習得する倉庫番スキル（並び替え・分類・鑑定・識別）と、報酬等で購入する設備（増設・仕分け・自動ピッキング）を分ける方向性を記録しました。Phase 3 の購入機能で全スキルを購入させると確定せず、個別機能の選択時に獲得・解放条件を判断します。Phase 4 の性能・属性等の内部データと、能力によって開示される情報は分離する方針です。レア度は将来の星表示の構想で、現在の MVP には追加しません。

## 各実装タスク共通の確認

- 選択された機能 ID・所属フェーズと今回の範囲を明記し、実際の依存関係を確認して必要な未決定事項を解消する。選ばれていない機能を先回りして実装しない。
