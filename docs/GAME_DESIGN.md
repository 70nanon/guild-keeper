## 作品コンセプト（確定）

**「勇者にはならない。勇者を倉庫から支える。」**

才能はあるのに整理整頓が壊滅的に苦手な勇者が、既存のギルドの紹介で倉庫番を雇います。プレイヤーは装備の支給、持ち帰られた戦利品の整理、倉庫の効率化を担当します。冒険・戦闘を直接操作せず、裏方の日常業務から物語に関わります。

**主題：「ただ倉庫を整理していたら、いつの間にか世界を救う手助けをしていた」**

- 開発上のプロジェクト名と現在の表示タイトル：**Guild Keeper**。今回は変更しません。
- 作品の仮称：勇者の倉庫番。正式なタイトル変更は別タスクでまとめて行います。
- ジャンル：倉庫整理 × アイテムピッキング × 効率化 × 自動化。
- 対象：PC・スマートフォンのブラウザ。

物語が大きくなっても、主役は倉庫に並ぶ大量のアイテムと、その作業改善です。勇者の直接操作、戦闘アクション、キャラクター育成、ギルド経営全般を主目的にしません。ファンタジー世界は、倉庫を管理する日常を楽しくする舞台です。

## コアとなる面白さ・基本方針（確定）

**途方もない量の単純作業を、プレイヤー自身の工夫、倉庫番スキル、設備によって効率化すること。**

「こう整理すれば次から楽になる」「こんな機能があれば便利なのに」という発見を、自分の配置や能力・設備の成長につなげます。雑然とした大量の品が徐々に整い、倉庫の景色が変わる視覚的な快感も重視します。

- ひとつの倉庫を継続して管理し、ステージごとの初期化を基本ループにしません。
- 大量の品があること自体を体験に含めます。整理方法にひとつの正解を押しつけず、整理を毎日の義務にしません。
- 原則として制限時間・ゲームオーバーを設けず、自分のペースで作業し、任意に日を進める方針を維持します。冒険の全滅・復帰に関する例外案は未決定です。
- 成長で操作・作業方法と、アイテムから読み取れる情報が変わります。現行 MVP の機能を遡って封鎖する指示ではありません。
- 人員・物量が増える頃には、それを扱う効率化手段も増えるようにします。自動化後も分類ルール・需要・在庫配分などの判断を残します。
- PC・スマホで、ドラッグ必須にせず操作できるようにします。

## v0.1 MVP の暫定仕様

基本操作の検証のため、ユーザーの明示的な依頼により F-001・F-002・F-003・F-005・F-006・F-007 をひとつの PR で実装します。将来の経済・成長・日次ループの詳細を確定するものではありません。

- 初期倉庫は96枠・96個。8品目（剣、盾、回復薬、杖、薬草、兜、魔力の雫、靴）を各12個配置する。1枠1個でスタックせず、個体に一意の ID を持たせる。配置は再現可能な混在配置とし、リセット時も同じ状態に戻す。
- 勇者はひとり。固定の注文3件を順番に表示する。注文1は剣1・盾1・回復薬2、注文2は杖1・魔力の雫2・薬草1、注文3は兜1・靴1・回復薬1・薬草2。初期在庫で全件を達成可能にする。
- 品をタップ・クリックして選択。同じ品を再度選ぶと解除する。「納品する」で注文の未充足品を1個ずつ渡し、個体を在庫から取り除く。位置は詰めず空き枠を残す。不適合品・必要数を超える品は消費せず、理由を表示する。
- 「入れ替える」後に移動先をタップして品同士の交換か空き枠への移動を行う。元の枠を押すと移動モードを取り消し、解除ボタンで選択自体も取り消す。移動先を選ぶ間は納品しない。
- 数量を満たした時点で完了を表示する。「次の注文へ」で次の固定注文を表示し、在庫と配置は保つ。最終注文完了後は「最初から遊ぶ」で在庫・配置・注文進捗・選択をリセットする。
- **固定注文の連続表示とリプレイは MVP 用の暫定挙動であり、日送り・帰還を含む正式な日次サイクル（F-009）ではない。** 通常プレイ中に倉庫を初期化するステージ制にはしない。リプレイ時の初期化だけを明示的に行う。
- 同一ページで注文、倉庫、操作欄を扱う。ドラッグ不要のボタン操作とし、選択状態を色とチェックで示す。納品候補のハイライト（F-011）や本格的なアイコン制作（F-004）は行わず、品名・種類と基本8品目の独自 SVG アイコン試作を使用する。
- 初回 MVP では帰還・入荷も対象外だったが、現在は次節の F-008 手動帰還を追加する。日送り、保存、アップグレード、自動化、複数倉庫・冒険者、性能・レアリティ、バックエンドは引き続き対象外。再読み込みは初期状態へ戻る。

将来の序盤で操作や情報を制限する構想は、この MVP へ適用しません。並び替えと詳細な品名は基本操作の検証のため維持します。本節以外の初期件数・スタック・日次ルール等の未決定事項は、長期仕様についての判断事項として残します。MVP の数値・品目は将来のバランスを確定しません。

## F-008：手動帰還・ランダム入荷の暫定仕様

この機能は日次サイクル F-009 とは独立した MVP の検証用操作です。初期96枠・8品目・固定注文は変えません。

- **契機**：注文完了後に「勇者の帰還」を押す。注文1件につき帰還は1回。未完了の依頼は処理せず、ボタンの依頼 ID と処理済み記録を検証して連打・古い操作による重複を防ぐ。
- **返却**：支給した武器・防具（剣・盾・杖・兜・靴）は100%返却し、元の個体 ID を維持する。回復薬・薬草・魔力の雫は全て使用済みとして返却しない。破損・返却率の抽選は導入しない。
- **戦利品**：2〜4個を同じ確率で抽選する。各品は既存8品目から等確率で独立抽選し、同品目の複数入荷を許す。帰還の依頼 ID と通し番号から専用の個体 ID を作り、初期品・別依頼の戦利品と区別する。新しい品目・性能・属性・レア度は追加しない。
- **配置**：既存の空き枠だけを無作為に選ぶ。占有中の枠は変更せず、プレイヤーの入れ替え・配置を維持する。現在選択中の品と移動モードは帰還処理後に解除する。
- **容量不足**：枠数を増やしたり在庫を上書きせず、入りきらない品の個体を「受取待ち」へ保持する。古い受取待ち、今回の返却装備、今回の戦利品の順に、入る分だけ空き枠へ配置する。受取待ちは追加倉庫ではなく入庫待ちの安全バッファで、直接選択・納品はできない。
- **再入庫**：「受取待ちを入庫」で、その時点の空き枠に再配置する。空きがなければ何も消費せず保持。部分的に入る場合は残りを保持し、再試行しても品目・数量・個体を再生成しない。並べ替えだけでは空き数は増えず、納品で空きを作れる。全注文完了後に空きがなければ、そのプレイ中は残りを受取待ちとして保持する。廃棄や容量拡張の機能は追加しない。
- **コメント**：帰還時に3種類の短文からひとつを表示する。返却・消耗・戦利品の個数も表示するが、冒険の成否・スコア・装備の性能による結果分岐は実装しない。コメントは最新1件を残す。
- **既存の進行**：「次の注文へ」は帰還を必須にしない。帰還を飛ばした注文の支給記録も保持し、完了した依頼の古い順に後から帰還できる。次の注文の途中や最終注文完了後でも、以前の完了依頼を処理できる。これは固定注文の検証用で、複数冒険者や時間経過を追加したものではない。
- **乱数と重複防止**：UI が操作時に乱数シードを渡し、ロジックは同じ状態・シードから同じ結果を得る。React の再評価で抽選が変わらない。処理済み依頼は再帰還せず、受取待ちを入庫しても抽選し直さない。
- **リプレイ・再読み込み**：既存の「最初から遊ぶ」は、在庫・注文・支給記録・帰還済み記録・受取待ち・コメントを全て初期化する。セーブはないため再読み込みでも初期化する。受取待ちの保持保証は現在のプレイ中の容量不足処理に対するもので、リプレイやページ破棄を越す保存ではない。

返却率、消耗率、戦利品のテーブル・量、コメント、受取待ちの扱いは MVP の暫定ルールです。長期の冒険・日送り・報告書・保存仕様を確定しません。F-009 は未実装のままです。

## ストーリーと業務規模（方向性合意）

| 段階 | 物語と倉庫の仕事 |
| --- | --- |
| 雇用と初仕事 | 成長に行き詰まる勇者が倉庫番を雇う。大まかな装備の依頼を受け、品を探して支給する |
| 倉庫番の成長 | 勇者が戦利品を無造作に戻す。仕事を重ね、操作・情報・設備を増やす |
| パーティ結成 | 仲間が増え、複数人分の装備支給を、身についた効率化で支える |
| ギルド設立 | 勇者自身のギルドができ、大人数への支給・調達・レイド準備へ業務が拡大する |
| 魔王討伐 | 倉庫管理の能力と設備で大規模な出征を物流面から支える |

冒頭の紹介元のギルドと、後に勇者自身が設立するギルドは区別します。売却・仕入れも後半の構想に含まれますが、商取引・経営を主軸にすることは採用しません。既存の長期構想である強化・合成、素材確保、共通装備の使い回し、レイド用装備配分も維持します。各段階の人数、発生条件、長さ、具体的なイベントは未決定です。企画の初仕事の台詞例は方向性の例であり、MVP の固定注文を書き換える指示ではありません。

## 基本ゲームループ（長期方針）

1. 朝：勇者・パーティ・ギルドから装備や消耗品の依頼が届く。
2. ピッキング・支給：倉庫から条件に合う品を探して渡す。
3. 冒険：勇者たちが自律的に活動する。プレイヤーは戦闘を直接操作しない。
4. 帰還：短い冒険報告書と持ち帰った装備・戦利品を受け取る。
5. 整理・改善：品を並べ替え・分類し、業務達成と報酬でスキル・設備を充実させる。
6. 翌日：プレイヤーの操作で日を進め、新たな依頼を受ける。

既存の「注文 → ピッキング → 納品 → 自由整理 → 帰還 → 翌日」を置き換える強制的な進行仕様ではありません。整理は帰還の前後に自由に行える方向を維持します。報告書・冒険は既存の帰還と成長へ文脈を加える構想です。帰還・日送りの発火順、未完了注文時の扱い、整理可能な時点の具体的制約は今後判断します。

支援で勇者が前進 → 業務規模・戦利品が増える → 倉庫管理が上達・自動化 → さらに大きな冒険を支える、という循環を目指します。MVP の固定注文3件はこの日次ループの完成ではありません。

## 倉庫・アイテム・注文

- **倉庫**：在庫と配置を継続して管理する作業空間。初期はひとつの大きなインベントリ。分類倉庫・保管枠の増設は設備の構想。長期の容量、上限、入荷超過時の処理は未決定。
- **アイテム**：装備・消耗品・戦利品、後半には素材も想定。種類・属性・レア度・用途などのタグ化は候補であり、正式データ仕様は未決定。現在の8品目には新しい属性・レア度を割り当てない。
- **注文**：冒険に必要な品を探して渡す仕事。勇者ひとりからパーティ・ギルドへ拡張する。将来は性能や属性等の条件が増える案があるが、条件式・数量・部分納品・欠品・報酬の長期ルールは未決定。MVP の採用ルールは変更しない。

## 冒険と報告書（方向性合意・詳細未決定）

成功・苦戦・撤退・失敗などを、短い文章と戦利品から何となく察する体験を目指します。明確なスコアを必須にせず、装備が成果へ影響しても、勇者の結果をプレイヤーが完全制御するゲームにはしません。冒険分析も強制しすぎません。

原則として失敗や撤退でも、素材・ガラクタ等を何かしら持ち帰り、倉庫作業の循環を止めない方向です。「強敵には勝てなかったが、逃げる途中で変な石を拾った」といった文章は企画例であり、実装済みのイベントではありません。最序盤の全滅は例外案としてありますが、条件・ペナルティ・復帰方法は未決定です。失敗を意図的に選ぶ方が有利になる調整は避けます。

冒険時間、報告書の生成・種類、装備と結果の関係、入荷量との接続は未決定です。詳細な冒険判定や報告書生成は未実装です。現在の F-008 は手動帰還と固定候補の短文コメントだけを扱い、長期の報告書システムの完成とはみなしません。

## UI・UX とアートの原則

村のギルド倉庫を思わせるゲームの道具として、倉庫セル・アイコン・注文書・選択状態・操作欄を統一します。一般的な SaaS の角丸カード群や絵文字の羅列ではなく、小さなシルエットを中心とする一覧を主役にします。アイコンの基本形・色・星による情報設計、素材感、表示密度は DESIGN_GUIDELINES.md を参照してください。

情報を成長で開示することと、操作状態を隠すことは区別します。名前・数量・選択・移動先・納品結果を読める状態にし、スマホでもドラッグなしで操作できます。装飾で倉庫の領域を圧迫しません。

## 今後の判断・検証事項

- 初期の操作制限と情報不足でも、作業が楽しく成立するか。
- 鑑定・分類・設備の獲得条件、解放順、経済と報酬。
- 属性色・補助記号・星数、情報の開示単位と、理不尽にならない識別難易度。
- 冒険と装備の影響、全滅・復帰、報告書・戦利品・容量のバランス。
- 人数・注文量の増加と自動化のタイミング、自動化後に残す判断。
- 生産・仕入れ・販売が経営全般へ主軸を移さないこと。
- 大量表示の目標件数・性能、モバイルの読みやすさと誤操作、保存・互換性。
- エンディングや制作優先度。資料の「基本ループ → 成長 → 冒険連動 → 規模拡大」は未確定の提案であり、ユーザーによる機能選択と個別の依存判定を置き換えない。
